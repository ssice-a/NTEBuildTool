# NTEBuildTool Context

This repository contains an Unreal Engine editor plugin for rebuilding and packaging NTE pak-only character mods from FModel exports and editable mirror-project assets.

## Domain Terms

- **Mirror Project**: The UE 5.6 project used to rebuild editable assets that match game content paths before cooking. In current verification work this is `F:\NTE\PhyLab`.
- **FModel Export Root**: The extracted source data under `F:\F-model\Output\Exports\HT\Content`. The plugin treats these paths as the source of truth for original game content layout and FModel JSON.
- **Game Container Scan Root**: The installed game root used for cooked-asset investigation. For NTE this must start at `F:\Neverness To Everness\Client\WindowsNoEditor`, not only `...\HT\Content\Paks`, because live assets and reference chains can sit in `HT\Content\PatchPaks`, `HT\Content\TagPatchPaks`, `HT\Content\Paks\Mods`, or other sibling container folders.
- **Game Mount**: The cooked output mount name used by the target game. For NTE this is `HT`, producing pak paths like `../../../HT/Content/...`.
- **Pakmod**: A mod distributed as cooked assets in `.pak/.utoc/.ucas` form. A pakmod can replace assets at identical game paths or add assets that are reachable through a replaced asset reference chain.
- **Replaced Asset**: A cooked asset whose `/Game/...` package path matches the original game asset path. Replaced assets are the reliable pure-pak entry point.
- **Added Asset**: A new asset under a mod subfolder such as `/Game/.../mod/Runtime/...`. Added assets must be referenced by a replaced asset, otherwise cook or the game may not load them.
- **Character Mod Workspace**: The target user-facing workflow for full NTE character replacement. It starts from one target appearance and coordinates the main mesh, multiple attached meshes, material-slot operations, runtime hotkey/UI actions, Kawaii physics presets, UI preview sync, and Package Plan generation. It supersedes the narrower Mesh Mod Workspace as the normal editor workflow.
- **CharacterModSpec**: The single source of truth for a Character Mod Workspace. It records the target appearance, source game paths, replacement main mesh, attached meshes, material operations, runtime toggle/action groups, Kawaii presets, generated asset names, and package preferences. UI dialogs load, edit, save, and pass this spec to feature modules; feature modules validate and transform it.
- **Character Material Plan**: The commandlet/editor-facing projection of `CharacterModSpec.MaterialOperations`. It resolves the target mesh and material slot, derives missing parent/output material paths, normalizes source-texture replacement maps, exposes material-operation warnings/errors, and contributes generated material instances plus replacement textures to package seeds.
- **HTPlayerAppearance / MeshAsset**: The game appearance data asset used by player outfits. It owns `FashionMeshData` for the main mesh and attached mesh arrays such as `ArrayFashionAttachedMeshData`. For character replacement, this is the preferred native place to register multiple attached meshes.
- **HTGame Stub Module**: A plugin runtime module named `HTGame` used only by the Mirror Project/tooling environment to save and cook assets with source-game script paths such as `/Script/HTGame.HTPlayerAppearance`. The target game already owns the real `HTGame` module; the stub is a schema bridge, not mod runtime code to ship as a DLL. Character package jobs that generate `HTPlayerAppearance` assets mark `RequiresHTGameStub=true`, so the package build can fail early if the Mirror Project restricts `NTEBuildTool` to Editor-only targets.
- **PlayerUIShow**: The UI preview Blueprint referenced by `DT_AppearanceData.UIActorClass`. Source-game examples often duplicate attached mesh preview components here through SCS child `HTSkeletalMeshComponentBudgeted` nodes. The tool should sync this from CharacterModSpec rather than forcing users to maintain it by hand.
- **Attached Mesh Runtime AnimBP**: A generated AnimBP assigned to an attached mesh. Its AnimGraph should inherit the parent pose when needed, apply Kawaii/secondary motion, and output the final pose. Its EventGraph can host hotkey/UI/save/apply logic for that attached mesh when runtime switching is required.
- **Runtime Anchor**: A loaded asset or runtime object that gives pure-pak logic an execution opportunity. The new preferred character path is native appearance loading through `HTPlayerAppearance` and attached mesh AnimBPs. A replaced `SkeletalMesh` with a generated Post Process Anim Blueprint remains a legacy/advanced anchor.
- **Runtime Anchor Mesh**: In the legacy PostProcess route, the `SkeletalMesh` that owns the Post Process Anim Blueprint used to tick pure-pak runtime logic. A `Skeleton` asset cannot be used as this anchor because it has no runtime component tick.
- **Runtime Action Plan**: The commandlet/editor-facing projection of `CharacterModSpec.RuntimeActions` plus `CharacterModSpec.RuntimeUi`. It groups actions by host mesh and host AnimBP, defaults action hosting to the main mesh unless `HostMeshId` explicitly chooses another mesh, resolves target component tags from action-level `TargetComponentTags` plus attached mesh `MeshComponentOwnedTags`, assigns shared runtime Widget/SaveGame output paths under the derived runtime root, derives a deterministic `SaveSlotName`, exposes the optional generated UI title/default-visibility/show-hide hotkey, and marks which action types are ready for Blueprint generation.
- **Runtime Action Writer**: The asset-writing side of the runtime-action module. It consumes `Runtime Action Plan`, creates or updates generated SaveGame, Widget, and host AnimBP Blueprint assets under the planned runtime root, stores auditable action data on those assets, contributes those packages to package planning, and generates the first EventGraph slice for owning-component and tag-resolved cross-component `MaterialSlotVisibility` / `AttachedMeshVisibility` actions. Generated host AnimBPs are created with the host mesh's Skeleton and preview mesh, load or create the generated SaveGame object during `BlueprintInitializeAnimation`, apply initial state from that SaveGame, create/add/toggle the generated runtime Widget when `RuntimeUi` is enabled, write action/UI state through hotkeys, and poll SaveGame-vs-local state during `BlueprintUpdateAnimation` before applying mesh or slot visibility changes. Generated Widgets build their button tree from the same action data and write button clicks back to the same SaveGame object. Attached-mesh CopyPose/Kawaii AnimGraph generation lives in the Kawaii writer; material swap/parameter changes, morphs, and main-mesh Kawaii source-pose strategy remain follow-up slices.
- **Target Mesh**: The mesh whose material slots, whole component visibility, material parameters, morphs, or future animation states should be toggled. It can be the main mesh, an attached mesh, or a separate mesh referenced by a runtime action.
- **StaticMesh Visibility Adapter**: Runtime logic used when the Target Mesh is a `StaticMesh`. `SkinnedMeshComponent::ShowMaterialSection` does not apply, so the controller must use a separate adapter such as material swapping to a hidden/transparent material.
- **Legacy Toggle Migration**: A one-time conversion from removed PostProcess/template toggle assets into `CharacterModSpec.RuntimeActions` and `RuntimeUi`. The plugin no longer loads, writes, audits, or packages `NTE.ModToggleSetup` or `NteMeshToggle` assets; preserved reports are historical evidence only.
- **Material Recipe**: A JSON description used to create or update a `MaterialInstanceConstant`, usually from an FModel material JSON plus explicit texture overrides. The preferred recipe format is authored around `SourceTextureOverrides`: the key is a source texture package used by the source material, the value is the mod texture package that should replace it. The material module expands that one source-texture replacement to every material parameter in the matching Source Texture Usage group. `TextureOverrides` remains the advanced per-parameter override format and wins when both formats write the same parameter. Raw FModel `MaterialInstanceConstant` exports are top-level JSON arrays; the material module normalizes those arrays into the internal `Parameters.Textures/Scalars/Colors/Switches` object before source texture usage is computed.
- **Material Proxy**: An editor-only stand-in for a missing cooked game parent material. It lets the Mirror Project create and inspect a mod `MaterialInstanceConstant` that intends to inherit a source game material path. A Material Proxy must not be treated as a Replaced Asset and should not be included in the pakmod package.
- **Source Texture Usage**: The grouped view of a source material's texture parameters, keyed by the source texture asset. It answers "which texture does this source material use, and which parameters use it?" so the user can replace one source texture once and have that new texture override every matching parameter.
- **Package Job**: A JSON description of a cook/package run. It lists the project, engine, game mount, output mods directory, mod name, package list, exclusions, and cook/pack options.
- **Versioned Runtime Blueprint Cook**: Package Jobs that include generated runtime Blueprints, especially Widget Blueprints, should cook with package versions enabled. The tool normalizes `Unversioned=true` back to `false` for generated runtime Blueprint packages because the target game can misread cooked UMG widget data and fail with bad export-index serialization errors.
- **Package Plan**: An editable candidate package list derived from one or more selected assets, usually starting from a selected mesh. It is a convenience preview, not an automatic decision: the tool shows selected packages, hard dependencies, candidate kinds, and reasons, then lets the user include or exclude packages before writing a Package Job. Skeleton, PhysicsAsset, source-game dependencies, and editor-only Material Proxy candidates are all user-controlled candidates; default inclusion is only a suggestion.
- **Mesh Mod Workspace**: The earlier user-facing workflow centered on one selected mesh. It remains a useful adapter for mesh/material/package operations, but the normal character replacement workflow should move to Character Mod Workspace.
- **Slot Material Operation**: A user-authored material change for one material slot, such as "slot 1 should use a new MaterialInstanceConstant derived from slot 0 and replace these source textures." It is the preferred material UI model because users think in mesh slots, parent/source materials, and texture replacements. The editor UI should let users fill slot assignment from the selected mesh, choose the parent material from a selected asset or an existing slot material, and choose replacement textures from selected texture assets instead of hand-writing package paths for common cases. The Mesh Mod Workspace can start a Slot Material Operation directly from a material-slot row; the material dialog receives defaults for mesh, slot, parent material, and output MaterialInstance path while the standalone FModel JSON entry remains an advanced adapter.
- **Package Workspace**: The package step inside the Mesh Mod Workspace. It starts from selected assets and generated mod assets, shows an editable Package Plan grouped by selected mesh, runtime assets, material instances, replacement textures, Skeleton/PhysicsAsset candidates, source-game dependencies, and editor-only Material Proxies, lets the user edit package job settings such as mod name, Mods output directory, job JSON path, and whether to immediately build, then writes a Package Job only after user confirmation.
- **Kawaii Preset**: The single reusable representation of editable KawaiiPhysics node settings, regardless of whether they were imported from source-game AnimBP/AnimLayer JSON, copied from another preset/template, authored manually from zero, or synchronized back from UE-edited generated assets. It preserves root bones, excluded bones, curves, limits, collision settings, generated DataAsset references, and NTE-specific fields, then applies resolved nodes to generated AnimBPs/DataAssets through one writer only when the mirror Kawaii schema matches the game usmap.
- **Character Asset Authoring Chain**: The cross-asset editing workflow documented in `docs/character-asset-authoring-chain.md`. It maps `CharacterModSpec` to editable UE assets, game schema stubs, Kawaii-compatible plugins, generated cooked packages, and package candidates so material, appearance, runtime, Kawaii, and cook UI stay consistent.

## Architectural Direction

The plugin should stay modular:

- Character Mod Workspace is the target orchestration UI. Mesh Mod Workspace and standalone dialogs are transitional or advanced adapters.
- CharacterModSpec should be the single source of truth that drives material creation, appearance assembly, runtime actions, Kawaii presets, and packaging.
- PhysicsAsset rebuild remains a narrow importer module.
- Material instance creation is a separate material module.
- Appearance assembly is a separate module responsible for `HTPlayerAppearance` / MeshAsset data and `PlayerUIShow` preview sync.
- Runtime hotkey/UI/material visibility generation is a separate runtime-action module. It should support material-slot visibility, mesh visibility, material swap/parameter changes, and future morph/animation actions from one spec model.
- Attached mesh AnimBP generation is the preferred pose/physics host for custom attached meshes. It should keep CopyPose/Kawaii in AnimGraph when needed; runtime switching logic defaults to the main host AnimBP and controls attached mesh components through tags, unless a runtime action explicitly sets `HostMeshId` to an attached mesh.
- Kawaii preset import/application is a separate module. The game usmap is the serialized schema authority; stock KawaiiPhysics compatibility must be proven before final cook.
- Kawaii import and manual authoring must converge on the same `Kawaii Preset` model. JSON import creates editable node candidates/seeds, not a separate generation path; package generation reads the resolved preset exactly the same way for imported and hand-authored chains.
- Character Workspace should expose UE-side Kawaii editing through the same model. Attached-mesh preset rows can apply their resolved Runtime AnimBP/DataAsset group from `KawaiiPlan`, open the generated AnimBP/Limits/Constraints assets for native Kawaii Details/Persona tuning, and sync edited asset values back into `CharacterModSpec.KawaiiPresets`; main-mesh rows stay blocked until a source-pose strategy protects the game's original character animation.
- Cook and IoStore packaging is a separate package pipeline module.
- Cross-asset authoring rules are tracked in `docs/character-asset-authoring-chain.md`; implementation and UI should follow its asset matrix instead of adding one-off per-feature package rules.
- The editor menu module wires these modules together and owns no large implementation.
- The material module should expose Source Texture Usage so users can see original texture groups and choose which source texture each new texture replaces.
- Material recipes should prefer source-texture-group replacement over isolated parameter replacement, because FModel materials commonly bind one texture to several parameters such as `PM_Diffuse` plus `ID_Tex`, `LightMap` plus a same-name mask parameter, or `PM_SpecularMasks` plus `NomralMap`.
- CharacterModSpec material operations should call the same material module as standalone recipes. `-ApplyMaterials` is the write path; plan-only reports must still expose effective output material paths and package seeds without mutating assets.
- Character Workspace material-slot actions should create/edit `CharacterModSpec.MaterialOperations`. The workspace loads/saves `CharacterModSpec` JSON, shows existing material operations from that spec, and upserts material slot actions back into the same file. Standalone material menus may still call the material module directly as advanced adapters, but they are not the workspace's core path.
- Character Workspace runtime-action actions create/edit `CharacterModSpec.RuntimeActions`. Material-slot visibility entries can be created from a material-slot row or the generic Runtime Action button; the removed legacy mesh-toggle menu has no runtime path.
- Runtime action asset generation should remain spec-first. `NteCharacterModSpec -ApplyRuntimeActions` writes generated Blueprint assets from `RuntimeActionPlan`; the current executable slice connects hotkey polling, generated Runtime UI buttons, SaveGame persistence, owning-component material-slot/attached-component visibility, and tag-resolved cross-component attached mesh visibility from the same action and `RuntimeUi` data.
- Character Workspace package actions should write confirmed package settings back into the active `CharacterModSpec` before creating or launching the package job.
- The package pipeline should build an editable Package Plan from selected assets before creating a Package Job; users remain in control of the final package list.
- Source asset inspection is an analysis-side workflow. The main creation chain should not require FModel source checks before material, toggle, or package steps.
- When source-game references are investigated with CUE4Parse/FModel tooling, scans should use the full Game Container Scan Root. A negative result from only `HT\Content\Paks` is not enough evidence that an asset or reference is absent.
- The toggle-runtime module should move toward configuration-driven UI and logic generation. Users define toggle items, labels, hotkeys, and material slots; templates should provide style and runtime anchor shape, not hardcoded item counts.
- Runtime action validation should reject blank labels and duplicate hotkeys before Blueprint generation so users do not get blank buttons or ambiguous input behaviour.
- Editor workflows should prefer the Character Mod Workspace interface over standalone path-entry dialogs. The standalone JSON and path dialogs remain useful advanced adapters for automation and debugging, but common pakmod creation should be driven by selecting appearances, meshes, attached meshes, material slots, hotkeys, textures, Kawaii presets, and package candidates directly in the editor.
- Old PostProcess-only compatibility branches and hardcoded test logic should be removed once the Character Mod Workspace module that replaces them is implemented and verified. Compatibility belongs in explicit migration tools, not permanent core complexity.

Pure pak remains the default strategy. A native DLL is only a fallback if evidence proves a target scenario has no reliable pure-pak runtime anchor. StaticMesh targets should first be attempted with a loaded Runtime Anchor Mesh plus a StaticMesh Visibility Adapter; adding a Post Process Anim Blueprint to a Skeleton is not a valid path.
